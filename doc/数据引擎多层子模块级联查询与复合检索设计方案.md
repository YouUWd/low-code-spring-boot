# 数据引擎多层子模块级联查询与复合检索设计方案 (100% 严密自洽版)

## 一、方案背景与核心命题

在低代码平台的数据引擎中，复杂的业务对象往往由一个核心主实体及其衍生的伴生实体、多层级从属实体共同构成。例如在“学生综合档案（101）”模块中，存在如下关系链条：
- 主表：`student`（学生基础信息）
- 1:1 伴生表：`student_profile`（扩展档案）
- N:1 维表：`clazz`（所属班级）
- 1:N 从表：`student_course`（选课明细）
- 1:N 孙表：`student_course_score_item`（课程考核构成明细）
- 1:N 曾孙表：`score_item_deduction`（分项扣分记录）

### 核心业务诉求
1. **全字段任意复合检索**：列表表头或检索面板中配置的任意层级字段（无论是主表、伴生表、还是 1:N:N:...:N 深层孙表字段），均可直接参与列表过滤；
2. **多层级数据一次性完整输出**：列表查询返回的数据行必须自动包含完整嵌套的子模块明细树；
3. **主表分页严格自洽**：分页 `LIMIT/OFFSET` 必须严格作用于主记录，绝不因 1:N 展开产生笛卡尔积膨胀或分页错乱；
4. **100% 严密自洽，杜绝猜测**：消除任何基于运行时盲搜（BFS 图搜索）产生的歧义（如菱形依赖多路径、中间表二义性）。

## 二、数学证明与第一性原理

### 1. 为什么“图搜索（Graph Search）”无法做到 100% 严密？
在一般的实体关系图（Entity-Relationship Graph）中，两张物理表之间可能存在多条合法的业务路径（例如 `project` 到 `sys_user` 既可以通过 `manager_id` 关联，也可以通过 `project_member` 中间表关联）。若运行时仅依据物理表名进行 BFS/DFS 搜索，必然存在信息论上的二义性死结（Ambiguity），导致算法有概率猜错业务意图。

### 2. 核心定理（模块树与路径唯一性）
> **定理（模块连接树定理）**：
> 若模块与子模块的组织结构构成一棵以根模块（Root Module）为根节点的有向有根树 $T = (V, E)$，且树中每个非根节点 $v \in V \setminus \{root\}$ 到其父节点 $parent(v)$ 均绑定唯一的表连接关系 $R(v) \in \text{sys\_table\_relation}$，则：
> 对于模块树中任意节点 $u$ 所属的任意字段 $f$，从根主表到字段所属物理表的 **JOIN 路径链条 $P(root, u)$ 在数学上有且仅有一条**。

**证明**：
根据图论基本性质，树是连通且无环的无向图。在有根树中，从根节点 $root$ 到任意节点 $u$ 的简单路径具有唯一性。因为每条树边 $(p, c)$ 都严格映射到一个确定的一对一或一对多物理表关联规则，故物理表级联连接链：
$$P = [ R(v_1), R(v_2), \dots, R(u) ] \quad (\text{其中 } root = v_0 \to v_1 \to \dots \to v_k = u)$$
也是唯一确定的，不存在任何分支选择或歧义。$\blacksquare$

## 三、元数据模型设计（Metadata Model）

要实现上述数学保证，元数据体系必须严格遵循 **“模块连接树（Module Join Tree）”** 规范：

```
                           [101] 学生综合档案 (Root)
                           Primary Table: student
                           伴生表: clazz (N:1), student_profile (1:1)
                                      │
                 ┌────────────────────┴────────────────────┐
                 ▼ (rel_1)                                 ▼ (rel_2)
          [102] 选课明细 (1:N)                       [103] 荣誉奖项 (1:N)
          Table: student_course                     Table: student_award
          Relation: student.id                      Relation: student.id
                  = sc.student_id                           = sa.student_id
                 │
                 ▼ (rel_3)
          [104] 考核构成明细 (1:N)
          Table: student_course_score_item
          Relation: sc.id = scsi.course_id
                 │
                 ▼ (rel_4)
          [105] 扣分细则 (1:N)
          Table: score_item_deduction
          Relation: scsi.id = sid.item_id
```

### 1. 模块表结构定义 (`sys_module`)
- `id`: 模块主键 ID
- `parent_id`: 父模块 ID（根模块为 0）
- `primary_table`: 当前模块的基准物理表名
- `relation_id`: 当前模块与其父模块 `parent_id` 之间的连接关系 ID（根模块为 NULL）

### 2. 字段元数据定义 (`sys_module_field`)
- `id`: 字段主键 ID
- `module_id`: 归属的模块 ID（**关键**：通过 `module_id` 定位其在模块树中的绝对坐标，从而唯一锁定 JOIN 路径）
- `table_name`: 物理表名
- `column_name`: 物理列名

### 3. 表关联关系定义 (`sys_table_relation`)
- `id`: 关系主键 ID
- `main_table`: 主键提供方物理表
- `main_field`: 主键字段名（如 `id`）
- `join_table`: 外键持有方物理表
- `join_field`: 外键字段名（如 `student_id`）
- `relation_type`: `1:1` 或 `1:N`

## 四、菱形依赖与自关联的消歧建模

### 1. 菱形依赖（Diamond Dependency）建模
如果业务中同一张物理表 `D` 可以通过两条不同的业务线连接到根实体 `A`：
- 路径 1：$A \xrightarrow{rel\_1} B \xrightarrow{rel\_3} D$
- 路径 2：$A \xrightarrow{rel\_2} C \xrightarrow{rel\_4} D$

**严密建模规则**：
在模块树中，表 `D` 必须被注册为两个不同的子模块节点（例如 `module_D1` 和 `module_D2`）：
```
        Module A (Root)
        ├── Module B (Parent=A, Relation=rel_1)
        │   └── Module D_via_B (Parent=B, Relation=rel_3, Table=D)
        │       └── 字段 D.name (归属 D_via_B) ──> 路径唯一确定: A -> B -> D
        │
        └── Module C (Parent=A, Relation=rel_2)
            └── Module D_via_C (Parent=C, Relation=rel_4, Table=D)
                └── 字段 D.name (归属 D_via_C) ──> 路径唯一确定: A -> C -> D
```
每个字段通过其绑定的 `module_id` 拥有唯一的上溯路径，**彻底消除菱形二义性**。

## 五、动态 SQL 生成算法（确定性复合检索）

当列表查询发起，接收到前端传入的检索条件 `filters` 时：

### 1. 过滤字段路径解析算法（Path Resolution）
```java
public class JoinPathResolver {

    /**
     * 根据字段所属的 moduleId，沿着 parent_id 向上回溯至根模块，提取确定性表连接链
     */
    public List<RelationStep> resolvePath(Long fieldModuleId, Long rootModuleId, Map<Long, SysModule> moduleMap, Map<Long, SysTableRelation> relationMap) {
        List<RelationStep> steps = new ArrayList<>();
        Long currModuleId = fieldModuleId;

        while (currModuleId != null && !currModuleId.equals(rootModuleId)) {
            SysModule curr = moduleMap.get(currModuleId);
            if (curr == null || curr.getRelationId() == null) {
                throw new IllegalStateException("模块树结构异常或缺少关联关系配置: moduleId=" + currModuleId);
            }
            SysTableRelation rel = relationMap.get(curr.getRelationId());
            steps.add(0, new RelationStep(curr, rel)); // 头部插入，保持自顶向下顺序
            currModuleId = curr.getParentId();
        }
        return steps;
    }
}
```

### 2. 结构化 SQL 组装规则
遍历所有检索条件，根据解析得到的 `steps` 路径进行分类：

1. **若 `steps.isEmpty()`（字段属于根模块主表）**：
   - 直接作为主查询的 `WHERE` 条件：`student.name LIKE '%张%'`。
2. **若 `steps` 中所有关系均为 `1:1` 或 `N:1`（平铺伴生表）**：
   - 主 SQL 自动 `LEFT JOIN clazz ON ...`，并在主 `WHERE` 中追加条件：`clazz.clazz_name LIKE '%一班%'`。
3. **若 `steps` 中包含任意 `1:N` 关系（多层级子模块）**：
   - 提取从根模块出发的第一条 1:N 边到目标孙表的所有连续边；
   - 自动合并相同子路径的过滤条件，组装为单一的 `WHERE EXISTS` 子查询：

```sql
EXISTS (
    SELECT 1 
    FROM `student_course` `sc`
    JOIN `student_course_score_item` `scsi` 
      ON `scsi`.`course_id` = `sc`.`id` AND `scsi`.`deleted` = 0
    JOIN `score_item_deduction` `sid`
      ON `sid`.`item_id` = `scsi`.`id` AND `sid`.`deleted` = 0
    WHERE `sc`.`student_id` = `student`.`id`
      AND `sc`.`deleted` = 0
      AND `scsi`.`item_name` = '期末考试'
      AND `sid`.`deduction_points` > 5
)
```

## 六、数据组装算法（Top-Down 批量并发提取 + Bottom-Up 递归归集）

为避免传统 ORM 的 $N+1$ 查询灾难，同时保证深层嵌套结构完整返回：

```
1. [阶段一：主记录分页]
   执行主表 LEFT JOIN SQL + WHERE (含 EXISTS) + LIMIT 10 OFFSET 0
   获取当前页命中主键：primaryIds = [2001, 2002, 2005]

2. [阶段二：子模块按层批量拉取]
   - Level 1: 查 student_course 
     WHERE student_id IN (2001, 2002, 2005) AND deleted = 0
     得到 courseIds = [501, 502, 503, 504]
   
   - Level 2: 查 student_course_score_item 
     WHERE course_id IN (501, 502, 503, 504) AND deleted = 0
     得到 itemIds = [1001, 1002, 1003]

   - Level 3: 查 score_item_deduction 
     WHERE item_id IN (1001, 1002, 1003) AND deleted = 0

3. [阶段三：内存自底向上归集 (Bottom-Up Assembly)]
   - 将 deduction 列表按 item_id 挂到 score_item 上；
   - 将 score_item 列表按 course_id 挂到 student_course 上；
   - 将 student_course 列表按 student_id 挂到 student 主记录上。
```

### 性能与正确性保证：
- **查询次数常数级**：无论当前页有多少学生、多少课程、多少明细，整棵树加载所执行的 SQL 数量严格等于 **子模块节点数 + 1**，绝无 $N+1$；
- **分页 100% 精确**：主表 `COUNT(*)` 和分页 SQL 始终独立计算，彻底隔绝笛卡尔积膨胀。

## 七、权限体系与数据脱敏对接

在全链路统一采用 `tableName`、`columnName`、`view`、`apply`、`edit` 的规范下：
1. **数据脱敏**：在执行完阶段三的自底向上归集后，根据当前角色的 `view` 权限矩阵，遍历整棵结果树，对 `view == 0` 的字段执行置空或掩码（Masking）处理；
2. **写权限校验**：保存时严格按各层实体的物理表名与列名，校验 `apply`（新增）或 `edit`（修改）权限。
